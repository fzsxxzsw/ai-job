# 求职自动化与复盘接入说明

本地版本 0.0.71 在现有 Python 9100、Agent 9101、MySQL 和固定 Chrome 扩展中接入统一任务协议。GitHub 推送暂缓。代码完成、隔离验收、本地发布和 Chrome 页面验收是不同状态，应以对应证据判断是否完成。

## 实际执行链路

助手正常收到的消息或用户启动的投递流程创建任务。Agent 使用命名 LangGraph 流程收集资料、生成决定、校验、保存，随后等待浏览器动作回执或人工确认。浏览器只能执行固定动作；服务端再次检查账户、暂停开关、会话新消息、筛选设置和已批准的内容。

回复草稿不会提前写成已发送历史。联系岗位与发送招呼分别记录结果；联系成功后查联系人失败不会重复联系。手机号、微信和简历交换需要对应请求的明确批准。手工编辑并发送的单条消息保留原有手动流程。

任务能显示当前阶段、所需确认、动作状态和错误。服务中断后使用数据库记录及 LangGraph 检查点恢复。发送结果不明时显示待核实，不能盲目重发。业务完成还需要图的 END 检查点确认，避免服务重启后遗留未完成的图。

## 投递记录与复盘

界面包含投递记录与统计、简历版本、复盘与下一轮策略三个视图。历史快照按当前用户显式导入，不改写旧记录；追加确认或纠正保留原事件。

统计使用固定 7、14、30 天观察窗口，显示分子、分母、排除原因和可查看的样本。沟通后的回复、面试和 Offer 使用首次确认联系时间；附件后的面试使用确认发送附件的时间。观察期未满、附件版本未知或混用时如实排除相关指标。后来被拒绝不会抹掉此前已发生的面试。

准备使用的简历不等于已经发送的附件。简历正文、哈希和版本关系不可变；用户确认具体附件版本后才可据此归因。选择版本会影响后续图中的筛选输入，但不会自动上传或替换平台附件。

复盘调用已有的分析模型路由，结合已确认反馈、岗位资料和简历事实生成有证据的问题和解释；统计、约束、预算和批准内容由代码校验。模型失败或输出越界会明确显示规则分析。输入预算和遗漏资料可见，不将部分资料描述为完整分析。

确认复盘不会自动接受简历修改或启动投递。简历修改需先预览并单独接受；策略需先批准再应用，应用后仍沿用现有人工启动和暂停控制。更改筛选设置后旧策略须重新核对。预算不会因重复应用同一策略而重置。

## 当前边界

- 正常收到的明确拒绝或正面回复可以作为自动分析资料。现有被动协议尚不能证明会话最新末尾和连续完整性，因此不能把真实已读不回、未读不回判定标成已完成平台验收；证据不足时保留未知。
- 简历自动补丁目前只整理原文格式；事实缺口以待确认问题呈现，不自动改写经历。策略目前执行一个明确目标组的版本和预算，不宣称完成多组自动优化。
- 样本量达到 20 仍不能证明岗位方向、级别和渠道可比，统计不宣称某版本导致更好结果，也不会自动训练模型。
- 删除复盘会清除对应业务私有内容，并等待 Agent 删除检查点后才显示完成。已接受的版本、已批准的引用和投递事实保留；本地数据库备份独立保留，不属于此删除操作。

## 本地启用与验收

配置默认关闭新流程。显式设置 `API_AUTOMATION_ENABLED=true` 同时启用 API 和 Compose 中的 Agent 工作线程；`API_CAREER_ENABLED=true` 启用职业记录和复盘界面。不得只改界面状态冒充任务已经运行。

构建使用 `build-job-helper.ps1`，发布使用 `release-job-helper.ps1 -ApplyMigrations -DatabaseBackupPath <新的备份路径>`。发布在停止旧写入服务后创建新备份，保留一个当前版本和一个回滚版本，并暂停当前用户的 AI 回复；成功或回滚均不自动恢复发送。

本地服务及固定扩展目录更新后，还需核对已安装扩展与实际页面显示的版本和 build ID。未经明确授权，不操作用户 Chrome/BOSS 页面；服务健康和本地构建成功不能替代页面验收。

内部协议详见 [统一任务契约](../ai-job-api/UNIFIED_CAREER_CONTRACT.md)。真实数据副本迁移、故障恢复、模型边界、界面渲染和独立复核证据保存在本轮 JobHelper 备份目录，正式发布结论需使用最终冻结源码对应的结果。
