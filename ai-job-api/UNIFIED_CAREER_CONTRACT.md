## Common rules

Existing response envelope, session authentication, origin checks and inactive-owner/read-only checks apply. Public payloads reject extra fields and do not accept userId. Internal endpoints reuse the fixed configured API URL and `X-Internal-Token`; runtime credentials/leases never enter checkpoints. IDs are opaque case-sensitive strings; times are Unix milliseconds; request IDs bind to a normalized payload hash (same ID/different input is 409). Bounded request sizes and existing model routing/quotas apply.

Feature configuration: `API_AUTOMATION_ENABLED` / `API_CAREER_ENABLED` on API; `AGENT_AUTOMATION_ENABLED` on Agent. Default false in generic settings/tests; explicitly enable the verified local deployment. Turning orchestration on must not enable the user's reply/delivery switches. The browser uses the server mode and never silently falls back to direct generation/sending when the enabled graph is unavailable. Legacy HTTP shapes remain compatible when orchestration is off; enabled mode must fence old sendable reply/filter bypasses.

## Public automation API

Prefix `/api/job/automation`.

`GET /status` returns `{contractVersion:1,enabled,mode:"LANGGRAPH"|"LEGACY",agent:{state:"READY"|"STALE"|"OFFLINE",lastSeenAt,lastCompletedAt,lastErrorCode},executor:{state:"READY"|"STALE"|"OFFLINE",lastSeenAt},counts:{queued,running,waitingExecution,waitingConfirmation,uncertain,failed,completed},outcomes:{enabled,caseCount,reportCount,lastObservedAt},buildId}`. Counts are owner-scoped. A fresh worker heartbeat proves worker contact only; display actual completed tasks separately. No raw exception text or private configuration.

`POST /executors/heartbeat` input `{executorId,platformAccount,capabilities:[ActionKind],replyEnabled:boolean,deliveryEnabled:boolean}`. Binds this executor to the signed-in owner and platform account, records freshness, and returns `{executorId,authorizationRevision,leaseUntil}`. It does not turn server preferences on. Subsequent changes to pause/scope/config invalidate execution authority. Platform credentials/security tokens remain in the browser.

`POST /jobs` input `{requestId,kind:"REPLY"|"APPLICATION",platformAccount,conversationKey,encryptJobId,bossId,input}`. Nullable bindings are permitted for an application before recruiter resolution; a reply requires a verified conversation/peer and real inbound event identity. `input` is a discriminated validated shape:

- REPLY: `{inboundMessageId,inboundSentAt,question,jobKey,jobInfo,exchangeRequest}`. `jobInfo` follows existing AskInput. `exchangeRequest` is null or `{kind:"ACCEPT_PHONE"|"ACCEPT_WECHAT"|"ACCEPT_RESUME",requestMessageId}` bound to the observed platform request. Recovered text without a stable platform MID cannot independently authorize exchange or a duplicate reply; hold it for association rather than minting a random event ID. A repeated platform message remains the same request across restarts/tabs.
- APPLICATION: `{cycleKey,filterInput,localAssessment:{passed:boolean,reason:string},greeting:{enabled:boolean,text:string},preparedResumeVersionId,strategyPlanId}`. `filterInput` is existing FilterInput. `cycleKey` is stable for one genuine attempt and retained across retries. Browser local assessment preserves all hard filters; LangGraph invokes the backend filter and owns the final contact decision. Current user preferences/active resume are read and frozen server-side, never trusted from submitted hashes. A failed hard assessment cannot be overridden by the model. Selected resume/strategy must belong to the owner and be approved/applicable.

Response is JobView. `GET /jobs?limit&offset&kind&conversationKey` and `GET /jobs/{jobId}` return owner-scoped views. View fields: `{jobId,kind,status,phase,revision,inputHash,createdAt,updatedAt,lastErrorCode,decision,actions:[ActionView],result,phaseHistory}`; public inputHash is non-secret, private input bundles are omitted. Status `READY|RUNNING|RETRY|WAITING_EXECUTION|EXECUTION_READY|WAITING_CONFIRMATION|CONFIRMATION_READY|COMPLETED|SUPERSEDED|CANCELLED|FAILED|UNCERTAIN`. `POST /jobs/{jobId}/cancel` input `{requestId}` cancels undispatched actions and prevents new execution; already dispatched actions retain their receipt/reconciliation state.

`POST /actions/claim` input `{executorId,platformAccount,jobId}` returns null or one ActionView plus runtime `{leaseToken,leaseUntil,authorizationRevision}`. Claim is limited to the explicit job and verified account, fixed supported kind, and active user authority. Never return another conversation's work merely because it is globally next in a queue.

ActionKind: `CONTACT_JOB|SEND_GREETING|SEND_TEXT|SEND_RESUME|ACCEPT_PHONE|ACCEPT_WECHAT|ACCEPT_RESUME`. Each side effect has its own persistent action ID and result, including greeting separately from successful contact. ActionView `{actionId,jobId,kind,status,sequence,clientMid,payload,lastErrorCode}`. Payload contains only fixed business data: bounded text/subject IDs/original request MID; never platform auth/security tokens. Existing browser context resolves the original exact job/contact locally. If lost or ambiguous, action waits visibly; never guess another contact.

`POST /actions/{actionId}/dispatch` input `{executorId,platformAccount,leaseToken,authorizationRevision,clientMid}`. Atomically transitions a still permitted LEASED action to DISPATCHING before any platform side effect, rechecking live user switch/session stop, current inbound generation, preference/resume binding and prerequisite receipts. It returns `{actionId,status:"DISPATCHING",dispatchToken,clientMid}`. Persist the returned binding locally before invoking the platform. Repeated dispatch cannot grant a second execution.

`POST /actions/{actionId}/receipt` input `{requestId,executorId,platformAccount,dispatchToken,clientMid,status:"ACKNOWLEDGED"|"FAILED"|"UNKNOWN",serverMid,platformCode,occurredAt,errorCode}`. Text/greeting ACK requires an exact client/server MID binding. Non-message actions require a verified successful fixed platform response, not a promise resolving or HTTP200 alone. Dispatch token is a runtime receipt capability for the exact owner/action; a late matching ACK remains acceptable after lease expiry. Same receipt replays are idempotent; contradictory identifiers are 409. Missing or uncertain response is UNKNOWN and cannot trigger a resend.

Action states: `QUEUED|LEASED|DISPATCHING|ACKNOWLEDGED|FAILED|CANCELLED|UNKNOWN`. Expired LEASED before dispatch may safely return to the queue. Expired DISPATCHING becomes UNKNOWN, never QUEUED. A definite preflight failure before dispatch cancels/releases without sending. New HR input supersedes unsent drafts for that conversation; already dispatched results are recorded without permitting their stale follow-up operations. Server pause and final browser risk/config/account checks both apply.

## Internal graph protocol

Prefix `/internal/automation`. `POST /heartbeat` `{workerId,graphVersion,lastErrorCode}` reports actual compiled-worker operation. `POST /claim` `{workerId}` returns null or `{jobId,kind,revision,inputHash,leaseToken,leaseUntil,executionMode:"START"|"RESUME_EXECUTION"|"RESUME_CONFIRMATION",phase,artifactId,resultId,resumeData,context}`. Context is a minimal projection of IDs/flags; full private input remains on API. CAREER_REVIEW uses this same protocol, not a second owner table.

For `/jobs/{jobId}/{operation}`, common lease body `{leaseToken,revision,inputHash}`:

- `renew` -> `{jobId,leaseUntil}`.
- `gather` -> `{jobId,inputHash,ready,artifactId}` freezes/validates authenticated inputs and logs COLLECTING. Missing material is an explicit incomplete result, never invented.
- `compute` -> `{jobId,artifactId,reused}`; invokes existing task-routed filter or new pure reply draft computation, or career deterministic review + grounded proposal helpers. Durable artifact reuse avoids repeated model calls after restart. A provider-response/persist crash is visible uncertainty, not a promise of exactly-once billing.
- `validate` with `artifactId` -> `{jobId,artifactId,valid,errorCode}`. Independent output/evidence/action/ownership/constraint checks; no publish on invalid.
- `commit` with `artifactId` -> `{jobId,artifactId,status,waitFor:"EXECUTION"|"CONFIRMATION"|"NONE",resultId}`. Creates actions or review/proposals exactly once. Keeps lease until the actual LangGraph interrupt is persisted.
- `park` with `{artifactId,interruptId,waitFor}` -> `{jobId,status}`. Runs only after durable interrupt checkpoint, clears lease. If receipts/approval already arrived it makes the job resume-ready, never loses an early result.
- `complete` with `{artifactId}` -> `{jobId,status,resultId}`. Requires all required action receipts or bound approval; appends ACKed conversation history/application events exactly once; completes a no-action rejection/stop decision without calling a platform. Unknown action leaves a visible UNCERTAIN state.
- `retry` with `{errorCode}` -> `{jobId,status,nextAttemptAt}`. Fixed sanitized codes and capped backoff/attempts; no blind action resend.

Actual graph: collect -> compute/decide -> validate -> persist -> branch to durable execution/confirmation interrupt -> finalize -> END. Per-kind named graphs/nodes make traces meaningful. Runtime renewal remains separate during model work. Checkpoint reconstruction uses durable API artifacts/receipts/approvals; missing checkpoint never re-executes a dispatched action. Old outcome graph runs under the same Agent lifecycle and consolidated readiness but preserves its existing contract and task identity.

## Reply and browser integration

Split draft generation from sent-history mutation. The graph compute path must not call the current side-effecting conversation_reply wholesale. System prompt, model router, exclusion policy, high-interest pause and round limits remain effective. Draft is persisted independently; only acknowledged text increments sent rounds/history/notification state. Marking an inbound message processed must wait for required actions to ACK or an explicit terminal no-action decision. Ordinary analysis must not pause/enable replies.

Route both normal and recovered incoming handlers through job submission/dedup. Remove direct fire-and-forget preReplyMsg exchange acceptance in enabled mode. Phone, WeChat and resume consent require the specific original request and existing user authority; if no affirmative authority exists, expose WAITING_CONFIRMATION with a human action choice rather than default-consenting personal information. Human approval is bound to that exact action; it never enables other sends.

Route startPush through graph-owned filter decision and per-side-effect dispatch/receipt. Preserve existing local hard filters, interval/daily caps, risk stop, user pause and cross-tab delivery locks. Do not add active polling of BOSS or new unsolicited communication. Existing custom greeting text is used only when enabled; no new model-generated greeting is required.

Cutover: old queue entries must not be drained by an old worker alongside new graph work. Entries with proven ACK become receipt evidence; unacknowledged entries without a graph/action binding are visibly held for reconciliation. Never silently adopt an uncertain old send as safely retryable. Scope/account changes invalidate timers/subscriptions and action context.

Supply real current-conversation coverage only from observed exact message DOM/protocol data and verified latest position. No unread-list badge, local queue timestamp, empty heartbeat, generic MessageRead, or guessed terminal can prove peer read/unread or a complete conversation. Tests must exercise the actual installed handler adapter as well as its helpers.

Import is explicit local migration work, not model inference. Prepared/captured version never means attachment sent; imported exposure UNKNOWN. This does not overwrite active platform attachment or silently activate a resume.

Application revalidates hard constraints and total allocation<=budget. Applying never starts delivery or enables AI, and never silently changes salary/location/hard filters.

## Grounding and approval

Review stats are computed in code from a frozen authenticated bundle, never by model SQL or model arithmetic. Gap kinds `PRESENTATION_GAP|EVIDENCE_MISSING|SKILL_GAP|TARGET_MISMATCH|UNKNOWN`. Resume patches contain `{patchId,sectionId,originalText,proposedText,reasonType,factIds,feedbackEventIds,jdRefs,unansweredQuestions,verificationStatus}`. Unsupported numbers/employers/dates/degrees/skills are rejected or turned into questions. Validate original text against the base; submitted model fact IDs alone do not establish entailment. Safe deterministic presentation patches can be used if model output fails, with honest source and no invented content.

Strategy has objective, hard constraints, main/explore/pause groups, approved/prepared resume mapping, allocations, separated user preference versus observed evidence rationale, measurement window and uncertainties. A valid empty-data result explains insufficient samples; it cannot claim a best strategy or use another owner's cases. Bounded model calls use the existing router (analysis task), timeout, redaction and quotas. Do not introduce vector search, training, external resume upload or email sending for this feature.

## Agreed implementation clarifications

- A successful CONTACT_JOB receipt may additionally contain `resolvedBinding:{bossId,conversationKey}` derived from the exact successful platform response. This cannot rebind an already bound or unrelated conversation. It resolves subsequent greeting actions; other receipt kinds cannot mutate binding.
- ActionView additionally contains `payloadHash` and `approvalStatus:"NOT_REQUIRED"|"PENDING"|"APPROVED"|"DECLINED"`. `POST /actions/{actionId}/approval` input `{requestId,decision:"APPROVE"|"DECLINE",payloadHash}` records the exact action choice. Sensitive phone/WeChat/resume actions require affirmative specific approval in this version; no existing generic AI switch constitutes that approval. Declining is a terminal no-send result for that action, and does not strand unrelated acknowledged text.
- Fixed payloads: CONTACT_JOB `{encryptJobId,bossId,conversationKey}`; SEND_TEXT/SEND_GREETING add `text`; ACCEPT_PHONE/ACCEPT_WECHAT add `requestMessageId`; SEND_RESUME adds `resumeVersionId,platformResumeId`; ACCEPT_RESUME adds `requestMessageId,resumeVersionId,platformResumeId`. `resumeVersionId` is null without proof of the actual attachment content; a prepared version alone is not sufficient.
- REPLY input accepts `platformResumeId:string|null` default null from already known browser attachment configuration. A resume action with unknown platformResumeId cannot dispatch. The browser verifies the current exact attachment ID equals the approved payload before dispatch. This identifies an attachment without claiming its content matches an immutable career version. Successful platform receipt records exposure as UNKNOWN unless separately verified.
- Gather with ready=false still produces an honest incomplete/no-action artifact through compute/validate/commit; it cannot send. Claim resultId/artifactId are nullable before durable persistence. Checkpoint context contains only schema/job-kind/flags, while resumeData carries bounded receipt/approval IDs and statuses, not personal message bodies.
- `complete` additionally returns `waitFor:"EXECUTION"|"CONFIRMATION"|"NONE"`. Approving a sensitive action moves to a second durable execution wait, not job completion. Agent loops through persist-interrupt/park for the returned wait phase. Late ACK may wake a previously UNCERTAIN job for receipt finalization without granting any new send.
- Contact success is acknowledged before any recruiter lookup. The existing bounded recruiter lookup or later natural exact contact observation may resolve a missing binding with `POST /actions/{contactActionId}/binding` input `{requestId,platformAccount,bossId,conversationKey}`. Only an owned, same-account, ACKNOWLEDGED CONTACT_JOB accepts it; conflicts are409. Waiting greeting is then bound/woken. A failed lookup never downgrades successful contact to UNKNOWN or permits contact retry.

## Integration clarifications after independent failure probes

- Reply ordering uses an all-seen watermark in the authenticated owner/account/conversation, including terminal jobs. Known older input is rejected. A distinct event without comparable time returns a durable `UNCERTAIN` JobView with `INBOUND_ORDER_UNCERTAIN`, cancelling older undispatched drafts in the same scope; returning an error after rolling back this fence is incorrect. A heartbeat cannot resolve ambiguous order. Late exact receipts remain acceptable. Graph reply history and rounds use their own owner/account/conversation key, not the legacy job-wide session key; unknown legacy attribution is not imported into a recruiter conversation.
- Public GET automation jobs returns an array. Non-text action `clientMid` is null. Text client and server MIDs must be real, numeric, distinct, and uniquely bound to an action. The browser persists the original executor ID with its dispatch receipt so restart and late ACK use the original binding. UNKNOWN records the observation time, not evidence that a send succeeded. Manual, user-authored, single-recipient send controls remain manual; they are not described as graph automation.
- Required FAILED actions make the job FAILED and cancel dependent queued actions. Approving a sensitive action can require a second execution interrupt. `complete` returns `waitFor` and can return RUNNING only for that further wait; it must not report completion before required receipts.

### Final graph checkpoint acknowledgement

Business completion and durable graph END are separate acknowledgements. `complete` stores COMPLETED or FAILED with `graph_finalized=0` and retains the current lease. It supports a read-only, idempotent replay bound to the same owner/revision/inputHash/artifact, without restoring action authority. Renew accepts a legal terminal but unfinalized lease. Once the Agent verifies a durable END checkpoint, it posts `/internal/automation/jobs/{jobId}/graph-complete` with the common Artifact lease body, receiving `{jobId,status:"COMPLETED"|"FAILED",graphFinalized:true}`; this clears the lease and is idempotent.

Expired terminal-unfinalized jobs are claimable only as `executionMode:"RECONCILE_TERMINAL"`, `phase:"FINALIZING"`, with the existing artifact/result IDs. Public business status remains terminal. An existing pending finalize resumes; missing checkpoint goes directly to the named finalize node, skipping collection and computation. Existing END with lost ACK only replays read-only complete and graph-complete. Recovery never grants another browser dispatch. Real process-crash tests must verify both API-after-complete and graph-END-before-ACK gaps.

### Career confirmation and deletion

The generic decision code additionally permits `REVIEW_READY` for CAREER_REVIEW without browser actions. `POST /api/job/career/reviews/{jobId}/confirmation` takes `{requestId,decision:"CONFIRM"|"IGNORE",revision,inputHash}` and returns `{jobId,status}`. This confirms the viewed review version; it does not accept patches or apply a strategy. Patch acceptance and strategy approval remain separate explicit choices and do not silently confirm other pending choices.

Public manually entered application events may use USER_CONFIRMED or INFERRED. OBSERVED and FILE_VERIFIED evidence comes from validated internal platform observations/receipts or verified file content, not a client-selected enum. Prepared/selected resume content never establishes actual attachment exposure.

DELETE review creates an API tombstone, clears owned private review inputs/context/artifacts/results and unreferenced proposal bodies, cancels the task and revokes its lease atomically. Internal operations, including complete replay, return409 JOB_DELETED; ordinary claims exclude the tombstone. Delete and later GET return the minimal `{jobId,status:"DELETING"|"DELETED",checkpointDeleted:boolean}` without the erased body.

Agent cleanup protocol: POST `/internal/automation/cleanup/claim` `{workerId}` returns null or `{jobId,kind:"CAREER_REVIEW",cleanupId,leaseToken,leaseUntil}`; POST `/cleanup/{cleanupId}/renew` `{jobId,leaseToken}` returns `{cleanupId,leaseUntil}`; POST `/cleanup/{cleanupId}/complete` `{jobId,leaseToken,checkpointDeleted:true}` returns `{jobId,cleanupId,status:"DELETED"}` with idempotent completed ACK replay. API reports checkpointDeleted only after successful cleanup ACK. Agent first persists a no-body thread tombstone, then calls the installed checkpointer's actual `adelete_thread`. Writes must check the tombstone atomically across SQLite processes/connections so in-flight work cannot recreate deleted checkpoints. An in-memory lock alone is insufficient. Failure leaves cleanup reclaimable and never claims deletion completed. Immutable application facts and accepted/referenced resume versions survive review deletion; existing external backups have their own explicit retention.

### Final browser and career field semantics

- Receipts add `executionPhase:"BEFORE_PLATFORM_CALL"|"PLATFORM_RESULT"`, defaulting to PLATFORM_RESULT. BEFORE_PLATFORM_CALL accepts only FAILED, null platformCode/serverMid, and AUTHORIZATION_CHANGED or CONTEXT_LOST, bound to the original dispatch. It is legal only when the fixed platform function was never invoked. Once invoked, a timeout or unknown result is UNKNOWN/PLATFORM_RESULT, never a fabricated failed platform code.
- CONTACT_JOB ACK permits batch progress while its greeting remains pending. The same completed delivery run may finish only that already-authorized greeting with unchanged account, run, policy and pause/risk state. New contact actions still require an active delivery run. A new run cannot adopt old authority. Natural exact association has its own persistent browser record so a delayed GET cannot overwrite it.
- Browser inbound ordering separates observed from successfully submitted messages. A transient API failure retries the current unsubmitted MID with its existing request ID. Older events cannot revive, and unknown ordering remains a hold. Message ID numeric magnitude is not a substitute for observed event time.
- `GET /career/selection` returns `{preparedResumeVersionId,strategyPlanId}`. Selection cannot be inferred from the first page of versions. New user intents receive new request IDs; retries of a pending intent reuse that ID.
- Application `currentStage` is the historical confirmed stage: UNKNOWN, CONTACT_INITIATED, HR_REPLIED, INTERVIEW_INVITED, INTERVIEW_COMPLETED or OFFER_RECEIVED. `outcome` is OPEN, REJECTED, OFFER_RECEIVED or WITHDRAWN. `status` is the recorded outcome when present, otherwise the stage. The timeline separately identifies the most recent event.
- Actual exposure reports `verificationKind:USER_CONFIRMED|null`. In this implementation a user-confirmed exact version can be attributed; a platform attachment-ID ACK alone stays UNKNOWN. Do not label that ACK as verified file content.
- Analytics and frozen review evidence filter by confirmation and cutoff before applying superseding corrections. Inferred or future corrections cannot remove earlier confirmed facts from that cohort. `resumeInterviewRate` matures from the confirmed attachment-send event; other reply/interview/offer cohorts mature from first confirmed contact. Fixed sample IDs and exclusion reasons support drilldown.
- `descriptiveOnly` remains true while job family, level and channel comparability are unverified. Twenty samples alone does not establish comparability. `comparability.sampleThresholdMet` and `missingEvidence` distinguish sample size from those missing controls.

### Bounded model assistance

Career review calls the existing analysis model router once with a per-call attempt cap of three. Normal router callers retain their configured attempt count. Metrics, budgets, hard constraints, approval hashes and resume patches are computed and validated independently of model output.

The model selects exact references using three restricted relations: RECORDED_FEEDBACK, VERIFY_REQUIREMENT and COMPARE_RESUME_JD. Fixed code templates render the supported feedback description or a question to verify. Free-form invented skills, dates, achievements, causal conclusions and changes to allocations or patches are rejected. The assisted result records actual model name, selected evidence and explicit input coverage; invalid, unavailable or over-budget model work falls back to RULES_ONLY with a reason. `coverage.inputBytes` describes prepared messages, not proof of successful model delivery.

Current accepted resume patches perform formatting changes supported by the original text; they do not perform semantic experience rewriting. Current strategy execution binds one explicit target group, its prepared version and budget. It does not claim automatic multi-group optimization, attachment upload or model training. Review confirmation, patch acceptance, resume selection and strategy application remain distinct user choices.
